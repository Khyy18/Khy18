## Что нужно построить

### Архитектура (high-level)

```
[OKX Market Data] (websocket, 7 пар)
        ↓
[Feature pipeline] (классическая система — 50+ features)
        ↓
   ┌────┴────┬─────────┐
   ▼         ▼         ▼
[LSTM]   [LightGBM]  [PPO]    ← три ML-модели
direction regime+size  timing
   │         │         │
   └────┬────┴─────────┘
        ▼
[Decision Aggregator] (система — формула)
        ↓
[Risk Manager] (система — жёсткие правила)
        ↓ APPROVED
[Order Engine] (система — OKX API)
        ↓
[Telegram bot] (существующий UI на 80%)
```

### Принципы разделения

**ИИ решает (только это):**
1. LSTM — направление и магнитуда движения на 15-60 минут вперёд.
2. LightGBM — текущий market regime + multiplier для размера позиции [0..1].
3. PPO — timing исполнения (limit vs market, ждать или сейчас).

**Система решает всё остальное:**
- Все жёсткие правила риска (stop-loss, take-profit, kill-switch, GLOBAL_RISK_CAP).
- Конкретный qty в долларах (формула `risk_amount / stop_distance × multiplier`).
- API-исполнение, retry, обработка частичных fills.
- Telegram UI, мониторинг, логирование.
- Fallback при деградации ИИ.

### Fail-safe механики (обязательны)

1. **Без сигнала от LSTM** → новые сделки не открываются.
2. **При деградации ИИ** (Sharpe < 0.3 на 30-day rolling) → автоматический fallback на простую стратегию или DRY_RUN.
3. **При недоступности Groq** → AI-Gate fail-CLOSED, новые сделки блокируются (как сейчас).
4. **Закрытия работают БЕЗ ИИ** — stop-loss, take-profit, time-stop срабатывают сами.
5. **Auto-pause** при 3 LOSS подряд на паре (существующий механизм auto-block).

### Что нельзя делать в UI

- **Не использовать** `cat`, heredoc, ASCII-art за пределами `_card`. Только `_card` + `_label`.
- **Не использовать** обычный `-` (минус) для отрицательных чисел — только `_fmt_num`/`_fmt_pct`.
- **Не использовать** обычный пробел для разделения тысяч — только `_NBSP` через `_fmt_num`.
- **Не добавлять Markdown-обёртки** (`*bold*`, `_italic_`) — `parse_mode=HTML` стоит на уровне `send_message`.
- **Не использовать** em-dash `—` (U+2014) в новых пользовательских текстах. ASCII-дефис `-` или `_subhr_line()`.
- **Не использовать** новые эмодзи в заголовках кроме уже существующих в боте (`📊 📈 🛡 🎯 🔍 📝 🤖 🔑 ⏯ 🚨 🚫 🆘 📤 ⚙ ❓ 🏁`).
- **Не делать** карточки шире 30 символов в моноширинном виде — Telegram-клиенты на узких экранах ломают перенос.
- **Не вводить** новые цвета — только `🟢🟡🔴⚪` через `_status_dot`.

### Контрольный чек-лист перед релизом каждой UI-фичи

1. `python -m py_compile telegram_bot.py main.py memory.py config.py` — компилируется.
2. `grep -n 'set_keyboard' telegram_bot.py` — ровно одно определение, ровно 5 рядов кнопок (`[2,2,2,2,1]`).
3. `grep -n 'HR = "━" \* 24' telegram_bot.py` — константа на месте, не изменена.
4. `grep -n 'def _card\|def _label\|def _fmt_num\|def _fmt_pct\|def _progress_bar_10\|def _sparkline_8\|def _status_dot\|def _dir_arrow' telegram_bot.py` — все восемь хелперов на месте.
5. Для каждой адаптированной карточки — ASCII-mockup в комментарии docstring и реальная сверка через grep по якорям. **Не показывать пользователю mockup, который не соответствует коду.** Это steering-рулинг из прошлой сессии.
